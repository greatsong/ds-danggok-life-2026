7차시

배포 — 내 예측기를 인터넷에

🎯 오늘 만드는 것
  • 수명 예측기(배포 URL) — 내 앱이 인터넷 주소를 얻어 누구나 열어 볼 수 있게 된다
  • 상호 검증 기록 — 짝의 앱을 확인한 결과와 확인 한 줄 (수행평가 재료)

0. 왜 배우나

과학은 혼자 확인한 내용이 남의 검토를 거칠 때 지식이 됩니다. 우리가 쓰는 AnAge 데이터도 연구자들이 서로의 수치를 검토해 논문 근거와 함께 쌓아 온 결과물입니다. 그런데 우리 수명 예측기는 6차시까지 내 노트북 화면 안에서만 돌았습니다. 로그 척도를 골랐고, 어떤 집단을 볼지 정했고, 어디에 경고를 달지도 내가 정했는데, 그 판단을 확인해 준 사람은 아직 아무도 없습니다. 오늘은 이 앱에 인터넷 주소를 붙여 짝이 직접 슬라이더를 움직여 보게 만듭니다. 그 순간 내가 세운 조건이 처음으로 남 앞에서 확인을 받습니다. 배포에 한 차시를 통째로 쓰는 이유가 여기 있습니다.

1. 개념 이해 — 내 화면 밖으로 나가는 코드

배포는 왜 학습의 일부인가

내 컴퓨터에서만 도는 코드는 결과를 나만 봅니다. 그런데 데이터 분석의 목적은 결국 다른 사람을 설득하는 것입니다. 그래프와 숫자는 읽어 주는 사람이 있어야 완성됩니다. 배포는 내 분석을 "남이 직접 만져 볼 수 있는 물건"으로 바꾸는 일입니다. 남이 내 앱의 몸무게 슬라이더를 움직이는 순간, 내가 세운 조건들 — 로그 척도로 봤는지, 전체 동물을 봤는지 포유류만 봤는지, 관측 밖 몸무게에 경고를 달았는지 — 이 처음으로 남의 검증을 받습니다. 그래서 배포는 앱을 올리는 기술이면서 동시에 분석을 점검받는 학습 과정입니다.

남의 컴퓨터에는 내 것이 없다

배포 서버는 내 컴퓨터가 아닙니다. 내 컴퓨터에 깔아 둔 라이브러리도, 내 하드에 저장한 파일도 서버에는 없습니다. 그래서 두 가지 준비가 필요합니다. 첫째, requirements.txt — "이 앱을 돌리려면 이 도구들이 필요하다"는 준비물 목록입니다. 서버는 이 목록을 보고 라이브러리를 설치합니다. 둘째, 데이터는 내 컴퓨터의 파일 경로가 아니라 인터넷 주소로 불러와야 합니다. 우리 앱은 5차시부터 life_animals.csv를 주소로 불러 왔으니 이 조건은 이미 갖췄습니다. 첫 배포가 자주 실패하는 원인 대부분이 바로 이 "내 컴퓨터와 서버는 다르다"는 차이에서 나옵니다.

내 컴퓨터에서 실행배포된 앱
여는 사람나 하나주소를 아는 누구나
라이브러리내가 깔아 둔 것을 그대로 사용requirements.txt에 적힌 것만 설치됨
데이터내 하드의 파일도 열 수 있음인터넷 주소로 불러와야 함
코드를 고친 뒤다시 실행하면 끝깃허브에 다시 올리면 자동 갱신

상호 검증이 하는 일

같은 동물 데이터라도 척도와 집단을 다르게 잡으면 결론이 달라진다는 것을 6차시에서 봤습니다. 원척도로 보면 R²가 0.08, 로그로 보면 0.32, 포유류만 좁혀 보면 0.50이었습니다. 혼자 볼 때는 내가 고른 조건이 유일한 답처럼 보입니다. 그런데 내 앱을 남의 앱과 나란히 놓는 순간, "어떤 조건에서 어떤 답"인지가 비로소 드러납니다. 짝의 앱에 남기는 확인 한 줄은 흠집 내기가 아니라, 매 차시 해 온 "정말 그런가?" 확인을 서로에게 해 주는 일입니다. 만든 사람 혼자서는 자기 조건을 당연하게 여기기 쉬워서, 이 확인은 남이 해 줄 때 가장 잘 작동합니다.

2. 오늘의 목표

  • 6차시까지 우리 예측기는 한계까지 아는 앱이 됐습니다.
  • 이제 이걸 인터넷에 올려 주소 하나로 남과 나눕니다.
  • 배포 = 내 컴퓨터 안에만 있던 앱을 세상 어디서든 열 수 있게 하는 일입니다.

3. 배포 전 준비 — 파일 두 개

  • 배포에 꼭 필요한 파일은 두 개뿐입니다.
파일역할
main.py앱 본체 — 지금까지 만든 수명 예측기 코드
requirements.txt필요한 라이브러리 목록(scikit-learn·plotly)
  • 이 둘을 깃허브(GitHub) 저장소에 올려 두면, 스트림릿이 거기서 읽어 앱을 띄웁니다.
  • 깃허브 계정·저장소 만들기는 선생님 안내를 따릅니다(계정 정책은 학교마다 다릅니다).
💡 배포용으로 코드 다듬기 (①)
  • 먼저 앱을 한 화면에 깔끔히 정리하도록 AI에게 주문합니다.
① 샘플 프롬프트
지금까지 만든 동물 수명 예측기를 인터넷에 올릴 수 있게 한 화면으로 정리해 줘.
- 제목, 몸무게 슬라이더, 예측 수명, R² 점수, 외삽 경고 문구가 한 화면에 보이게 해 줘.
- 실제 점과 학습한 직선 그래프도 로그 축에 함께 넣어 줘.
- requirements.txt도 같이 줘. 버전 숫자 없이 이름만, 스트림릿·판다스·넘파이는 기본 설치라 빼고.
  • AI가 정리해 준 코드는 앞 차시들에서 이미 본 모습이라 여기선 다시 싣지 않습니다. (5차시 ② 참고)
③ 프롬프트 개선 예시
좋아, 이어서 고쳐 줘.
- 예측 몸무게가 데이터 범위를 벗어나면 '조심: 관측 밖 예측' 문구가 크게 뜨게 해 줘.
- 화면 맨 아래에 '이 예측을 어디까지 믿을지' 한 줄 안내를 넣어 줘(로그 척도·포유류 기준 등).

4. 스트림릿 클라우드에 올리기 (클릭)

  1. 배포 사이트 접속
    share.streamlit.io에 들어가 깃허브 계정으로 로그인. 처음이면 권한 허용을 눌러 줍니다
  2. 새 앱 만들기
    오른쪽 위 Create app(예전 이름: New app)을 누릅니다
  3. 내 저장소 고르기
    파일을 올려 둔 저장소(Repository)·브랜치(Branch)·파일 경로(main.py)를 고릅니다. 원하면 App URL에 기억하기 쉬운 주소를 정합니다
  4. 배포
    Deploy를 누르면 몇 분 안에 앱이 뜹니다. 생긴 주소(streamlit.app 으로 끝남)가 곧 내 예측기 주소
⚠️ 화면 구성은 조금씩 바뀔 수 있어요
  • 버튼 이름·위치는 스트림릿이 종종 바꿉니다. 못 찾으면 AI에게 "스트림릿 클라우드 배포 방법 알려 줘"라고 물어봅시다.
  • 배포는 처음엔 자주 실패합니다. 오류 메시지를 그대로 복사해 AI에게 보여 주면 대개 해결됩니다.
  • 코드를 고쳐 깃허브에 다시 올리면 앱도 자동으로 갱신됩니다.

5. 갤러리에 올리고 서로 검증

  1. 주소 게시
    배포된 앱 주소를 선생님이 안내하는 갤러리 주소에 올립니다
  2. 짝의 앱 눌러 보기
    다른 친구 앱을 열어 슬라이더를 움직여 봅니다. 좋아요와 한 줄 피드백을 남깁니다
  3. "정말 그런가?" 묻기
    피드백엔 칭찬만이 아니라 확인 한 줄을 꼭 넣습니다. 예: "포유류만 보면 답이 더 또렷하지 않아?"
💡 같은 데이터, 다른 결론
  • 남의 앱을 눌러 보면, 같은 동물 데이터인데 척도나 집단을 다르게 잡아 다른 결론을 낸 친구가 보입니다.
  • 누가 맞고 틀린 게 아니라, 어떤 조건에서 어떤 답인지가 다를 뿐입니다(6차시 세 조건).
⚠️ 오늘 산출물은 첫 증빙
  • 배포 주소는 수행평가와 갤러리의 첫 증빙입니다. 주소를 꼭 갤러리에 남깁시다.
  • 배포가 안 끝난 사람은 짝과 함께 마무리하거나 선생님 예비본으로 보충합니다.

6. 개념으로 다시 읽기 — 오늘 만난 장면 세 개

오늘 배포 과정에서 만난 장면을 1번의 개념 언어로 다시 읽어 봅니다.

장면개념으로 읽으면
배포 서버의 ModuleNotFoundError"배포 서버에는 내 컴퓨터의 라이브러리가 없다"는 사실의 확인 — requirements.txt에 scikit-learn·plotly를 적는 것이 해결책
깃허브에 다시 올리면 자동 갱신배포는 한 번 하고 끝나는 행사가 아니라, 코드를 고칠 때마다 새 버전이 나가는 통로 — 앞으로의 개선도 이 방식으로 나간다
같은 데이터, 다른 결론짝의 앱에서 본 다른 답 — 틀린 것이 아니라 조건(척도·집단)이 다른 것. 전체 3,188종에서 R² 0.32, 포유류만 좁히면 0.50이었다

7. 해보기 — 개인 또는 팀

✏️ 개인 미션 — 짝의 앱 검증 세 항목 (10분)
  • 갤러리에서 짝의 앱을 열고 세 가지를 확인해 기록한다.
  • ① 몸무게를 데이터 범위 밖(예: 대왕고래보다 무거운 값)으로 밀면 '조심: 관측 밖 예측' 문구가 뜨는가 → (뜬다 / 안 뜬다)
  • ② R² 점수가 화면에 보이는가 → (보인다 / 안 보인다)
  • ③ 이 앱의 결론이 어느 집단·어느 척도에서 나온 값인지 화면에서 알 수 있는가 → (알 수 있다 / 없다)
  • 확인 결과를 근거로 확인 한 줄을 만들어 갤러리 피드백에 남긴다. (예: "관측 밖으로 밀어도 경고가 없던데, 이 몸무게의 예상 수명을 그대로 믿어도 될까?")
🗣️ 팀 미션 — 받은 피드백을 개선 주문으로 (2~3인 토의, 7분)
  • 내가 받은 피드백 중 한 가지를 골라, 앱을 어떻게 고칠지 ③ 개선 주문 한 문장으로 만들어 본다.
  • 짝과 주문을 바꿔 읽고 확인한다: 이 주문은 화면에 보일 결과를 말하는가, 구현 방법까지 지시하는가?
  • 고친 코드를 깃허브에 다시 올리면 배포된 앱이 자동으로 갱신된다 — 개선의 순환이 인터넷 위에서 돈다.
🧾 배포 URL이 수행평가의 첫 증빙이다
  • 배포 주소는 클래스룸에 제출하고 갤러리에도 게시한다 — 수행평가와 갤러리의 첫 증빙.
  • 짝 앱 검증 기록과 확인 한 줄은 상호 검증 활동의 기록으로 남는다. 남긴 피드백을 캡처해 둘 것.

8. 확인 문제

지필 문항과 같은 유형입니다. 먼저 스스로 답을 적고 나서 펼쳐 보세요.

문제 1 — 내 컴퓨터에서 잘 돌던 앱이 배포하자마자 ModuleNotFoundError로 멈췄다. 원인과 해결 방법을 서술하시오.

예시 답안 — 배포 서버는 내 컴퓨터가 아니라서 내가 깔아 둔 라이브러리가 없다. requirements.txt에 필요한 라이브러리 이름(scikit-learn·plotly)을 적어 함께 올리면, 서버가 그 목록을 보고 설치한 뒤 앱을 띄운다.

문제 2 — 갤러리 피드백에 '칭찬 한 줄'만이 아니라 '확인 한 줄'을 꼭 넣게 하는 이유를 서술하시오.

예시 답안 — 분석 결과는 조건(척도·집단·관측 범위)에 따라 달라지는데, 만든 사람 혼자서는 자기 조건을 당연하게 여겨 확인하기 어렵다. "포유류만 보면 답이 더 또렷하지 않은가" 같은 확인이 숨은 조건을 드러내고, 결과를 언제 믿을 수 있는지 서로 확인해 주는 검증이 된다.

문제 3 — 같은 동물 데이터로 만든 두 앱이 서로 다른 R²(0.32와 0.50)를 보여 준다. 둘 중 하나가 틀렸다고 말할 수 있는가? 이유와 함께 서술하시오.

예시 답안 — 틀렸다고 말할 수 없다. 전체 3,188종을 본 값과 포유류만 좁혀 본 값처럼 조건(집단)이 다른 답일 수 있기 때문이다. 필요한 것은 승패 판정이 아니라 "어느 집단을, 어느 척도로 본 값인지"를 각 앱이 화면에 밝히는 것이다.

🎒 오늘의 체크 & 링크

  • 배포엔 main.py와 requirements.txt 두 파일이 필요하다
  • 배포 서버에는 내 컴퓨터의 라이브러리·파일이 없다 — requirements.txt가 준비물 목록이다
  • 깃허브에 파일을 올리고 share.streamlit.io에서 앱을 배포했다
  • 내 앱이 streamlit.app 주소를 얻었다
  • 주소를 갤러리에 올리고 짝의 앱에 좋아요·한 줄 피드백을 남겼다
  • 피드백에 '정말 그런가?' 확인 한 줄을 넣었다
